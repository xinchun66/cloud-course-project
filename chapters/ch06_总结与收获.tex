\section{总结与收获}

本次课程设计主要完成了两部分工作：一是在华为云 CCE 上部署后端、Redis 和前端服务，二是在同一套云环境中运行 Spark 分析任务。和本地实验相比，云端实验更容易暴露配置细节问题，例如镜像地址、Service 类型、PVC 绑定状态、HPA 指标采集和 Spark Driver 资源限制等。下面结合实际调试过程总结本次课设中的收获。

\subsection{云计算平台搭建总结}

\subsubsection{容器化与Kubernetes部署理解}

在开始做容器化之前，后端、前端和 Redis 更像是几个分散的组件。写完 Dockerfile 并用 Docker Compose 联调后，应用运行环境被固定到了镜像和 compose 配置里，后续再迁移到 CCE 时也有了明确的镜像来源和端口约定。

这部分最直接的收获是把 Dockerfile、容器、SWR 和 Kubernetes 部署流程串联起来。Dockerfile 负责构建镜像，Docker Compose 用来先在本地确认后端能连接 Redis，SWR 则提供 CCE 拉取镜像的位置。只要其中一个名称或 Tag 写错，Pod 就可能停留在镜像拉取阶段，后面排查镜像问题时这一点很明显。

Kubernetes 部署阶段主要围绕 Deployment、Pod 和 Service 展开。Deployment 管副本和滚动更新，Pod 承载具体容器，Service 负责访问入口和服务发现。只有把这几层关系放到实际的后端、前端和 Redis 部署里看，才能理解为什么 Pod 已经 Running 但接口仍可能访问失败，也能更快定位问题是在镜像、配置、Service 还是 ELB 绑定上。

公网访问部分也比本地环境复杂。LoadBalancer Service 并不会自动解决所有问题，CCE 侧还涉及 ELB 资源和注解绑定。后端接口最终能够通过公网 IP 返回 \verb|{"redis":"connected","status":"ok"}|，说明从浏览器或 curl 到 ELB、Service、Pod、Redis 的访问链路已经连通。

\subsubsection{配置分离、持久化与弹性伸缩理解}

ConfigMap、Secret、PVC 和 HPA 是本次课设中用得比较多的几类 Kubernetes 资源。

ConfigMap 与 Secret 解决的是配置放在哪里的问题。Redis 地址、端口这类普通配置放在 ConfigMap 中，密码放在 Secret 中，比直接写进镜像或代码更容易调整，也更符合部署环境经常变化的情况。

Redis 持久化实验验证了 PVC 的作用。删除 Redis Pod 后，新 Pod 还能读到之前写入的 \verb|testkey=hello|，这比单纯看到 PVC 处于 Bound 状态更有说服力。通过这个过程可以看出，Pod 可以重建，但数据卷需要独立保存。

HPA 实验中遇到的问题更多。压测工具、后台 curl 进程、Metrics Server 指标延迟都会影响观察结果。扩容不会立即发生，缩容也不会在停止压测后马上完成。这个过程说明，弹性伸缩依赖指标采集、控制器评估和 Pod 调度等多个环节，并不是简单修改副本数即可完成。

\subsection{Spark大数据分析总结}

\subsubsection{分布式数据处理流程理解}

Spark 部分使用豆瓣电影数据集完成数据清洗、统计查询和性能测试。相比只在本地运行脚本，将 SparkApplication 提交到 Kubernetes 后，需要同时关注代码、镜像、Driver 日志和 Executor 状态。

在 Spark 架构中，Driver 负责作业解析、任务调度和执行控制，而 Executor 负责实际的数据计算。用户提交的程序首先由 Driver 转换为执行计划，再将任务分发给多个 Executor 并行执行，最终汇总计算结果。与传统单机程序相比，Spark 能够充分利用集群资源处理更大规模的数据集。

数据清洗阶段主要使用 Spark DataFrame API 完成数据加载、Schema 查看、缺失值统计和字段处理。清洗策略不能只追求删除缺失值，还要看字段在后续查询中是否重要；核心字段缺失会影响统计结果，辅助字段则可以用占位值填充。

Spark SQL 查询部分覆盖了分组聚合、Top-N、年份趋势和窗口函数。几类查询写法不复杂，但在分布式环境中运行时，还需要通过 Driver 日志和结果截图确认作业确实在集群里完成。

Spark Operator 的作用也比较清楚：它把 Spark 作业变成 Kubernetes 中的 SparkApplication 资源，由控制器负责创建 Driver 和 Executor Pod。实际调试时，Driver 内存过小、镜像权限不足、依赖库缺失都会直接反映到 Pod 状态或日志中。

\subsubsection{性能对比与Amdahl定律理解}

性能分析实验比较了 Pandas、单 Executor PySpark 和双 Executor PySpark 的执行时间。

结果并没有出现“Executor 越多就一定越快”的线性关系。结合 Amdahl 定律看，程序中仍有一部分工作不能并行，作业启动、任务调度和结果汇总也会占用时间，所以增加计算资源后，加速比会受到限制。

本次数据规模只有几万条记录，Pandas 在单机上已经能很快完成查询。Spark 需要启动 Driver 和 Executor，还要经历调度、序列化和可能的 Shuffle，这些开销在小数据集上反而很明显。因此，分布式计算是否划算，要结合数据规模和任务类型判断。

这部分最大的收获是：性能优化不能只看“加节点”。如果数据量不大或通信开销占比高，增加 Executor 可能只能带来有限收益，甚至会让总耗时变长。

\subsection{课程设计反思}

\subsubsection{主要挑战}

本次课设最耗时的部分其实是排查云端环境中的连锁问题。镜像仓库、负载均衡、存储卷、Service、Pod 事件和日志经常需要结合查看，单看某一个页面很难直接判断根因。

Spark 部分也有类似情况。分析脚本没有打进镜像、数据路径不一致、镜像缓存未更新、Pandas 或 Matplotlib 缺失，都会导致 Driver 失败。排查时需要先看 Pod 状态，再看 Driver 日志，最后回到 Dockerfile、SparkApplication YAML 或数据路径上修改。

这些问题处理完之后，我们对 CCE、SWR、ELB、PVC、HPA 和 Spark Operator 之间的关系有了更清楚的认识。它们都在同一条部署链路中，前面的镜像、网络或权限配置出错，后面的 Pod、Service 或 Spark 作业就会受到影响。

\subsubsection{改进方向}

我们已经完成任务书要求的主要内容，但还有一些可以继续改进的地方。

一是 CI/CD 还可以做得更完整。目前流水线已经能构建镜像并推送 SWR，后续可以继续减少手工更新 Deployment 的步骤。二是 Spark 数据源可以进一步切换到 OBS，减少对仓库本地数据文件的依赖。三是监控和日志可以继续完善，把 Prometheus/Grafana 的指标和应用日志结合起来，排错时会更方便。

性能测试方面，如果有更大的数据集和更多节点，可以继续测试不同 Executor 数量下的耗时变化。这样得到的加速比会比当前小数据集更有参考价值。

这次课设把课堂上相对抽象的 Docker、Kubernetes、HPA、PVC、Spark 和 DDP 放到了同一个项目中。很多概念是在配置出错和排错过程中逐步理解清楚的，例如 Service 如何关联 Pod、PVC 为什么能保留数据、Spark 增加 Executor 后为什么不一定线性加速。后续如果继续做云原生或分布式计算相关项目，这些经验仍然有参考价值。
