\section{问题记录与解决方案}

课程设计在实施过程中涉及 Docker 容器、华为云 CCE 集群、Kubernetes 资源编排、Spark Operator 以及分布式数据分析等多个技术环节。由于实验环境复杂、组件依赖关系较多，在部署与验证过程中遇到了一系列典型问题。通过查阅官方文档、分析日志信息以及反复验证配置参数，最终逐步完成问题定位与解决。本章对实验过程中具有代表性的问题及其解决过程进行总结，以反映项目实施中的真实排错过程和技术积累。

\subsection{第一部分问题记录}

\subsubsection{镜像构建与推送问题}

在应用容器化阶段，首先遇到的问题是 Docker Hub 镜像拉取速度较慢甚至超时。例如在拉取 Redis、Alpine 等基础镜像时，多次出现网络连接超时、下载中断等情况，导致镜像构建无法正常完成。分析原因后发现，实验环境访问 Docker Hub 国际镜像仓库时网络延迟较高，部分镜像层下载不稳定。

针对该问题，一方面采用多次重试方式完成镜像拉取；另一方面优先使用已经成功下载的镜像作为基础镜像进行构建，避免重复访问远程仓库。对于课程设计所需镜像，还通过华为云 SWR 镜像仓库进行统一管理，使后续 Kubernetes 集群能够直接从 SWR 拉取镜像，减少对 Docker Hub 的依赖。

在镜像推送阶段，还出现了镜像标签不一致导致 Pod 无法启动的问题。具体表现为 Deployment 中引用的镜像标签与 SWR 中实际存在的标签不一致，导致 Kubernetes 无法正确拉取业务镜像。通过重新核对镜像名称、组织名称以及版本标签，并统一采用固定版本号管理策略，最终解决了镜像引用错误的问题。

此外，在 Spark 镜像构建过程中，还曾出现分析脚本未被正确打包到镜像中的问题。最初构建的 PySpark 镜像中缺少 \verb|analysis.py| 文件，导致 SparkApplication 提交后 Driver 容器无法找到入口程序。通过重新检查 Dockerfile 中的 COPY 指令，并验证镜像内部目录结构，最终成功将分析脚本打包至指定路径。

\subsubsection{CCE部署与网络访问问题}

在 Kubernetes 应用部署过程中，最典型的问题是后端 Service 长时间处于 \verb|EXTERNAL-IP=<pending>| 状态。虽然 Deployment 和 Pod 已经正常运行，但外部访问入口始终无法生成，导致后端接口无法通过公网访问。

通过分析发现，该问题并非应用本身故障，而是 LoadBalancer 类型 Service 尚未成功绑定华为云 ELB 资源。为解决该问题，在华为云控制台中创建共享型弹性负载均衡器，并通过 Service 注解指定 ELB 资源，随后 Service 成功获得公网 IP 地址，实现了后端接口的公网访问。

实验过程中还遇到了 kubectl 无法连接集群的问题。最初获得的 kubeconfig 文件使用的是 CloudShell 内网访问模式，其 API Server 地址为私有网络地址，仅能在特定网络环境下访问。当在独立 ECS 上使用该配置文件时，出现 API Server 连接超时错误。经过分析后确认问题来源于网络访问路径而非集群本身故障，后续通过重新获取正确的集群访问配置完成验证。

此外，在 Service、ConfigMap 和 Secret 等资源部署过程中，也曾出现资源名称拼写错误、命名空间不一致等问题。由于 Kubernetes 对资源名称高度敏感，细微的拼写差异都会导致应用启动失败。通过使用 \verb|kubectl describe| 和 \verb|kubectl logs| 查看详细信息，逐步定位问题并完成修正。

\subsubsection{PVC与HPA验证问题}

在 Redis 持久化实验中，PVC 创建后曾出现无法立即绑定存储资源的情况。经过检查发现，PVC 绑定过程依赖底层存储插件和 StorageClass 配置，当存储资源尚未完成分配时，PVC 会短暂处于 Pending 状态。等待存储卷创建完成后，PVC 成功进入 Bound 状态，后续 Redis Pod 能够正常挂载持久化卷。

在持久化验证过程中，还需要通过删除 Pod 并观察自动重建后的数据是否保留来证明 PVC 生效。实验初期曾担心 Pod 删除后数据丢失，但经过实际验证，重新创建的 Redis Pod 仍然能够读取此前写入的数据，证明持久化存储配置正确。

在 HPA 验证阶段，由于弹性伸缩依赖 metrics-server 提供资源指标，因此必须首先确认集群能够正常采集 CPU 和内存使用率。实际测试过程中发现，指标更新存在一定延迟，导致副本数不会立即发生变化。经过持续压测和观察后，最终确认 HPA 能够根据负载变化自动调整副本数量。该现象也表明 Kubernetes 的自动伸缩机制具有一定稳定窗口，以避免因短时间波动导致频繁扩缩容。

\subsection{第二部分问题记录}

\subsubsection{Spark作业提交问题}

在 Spark Operator 实验过程中，首先遇到的问题是镜像拉取失败。由于 Spark Operator 默认引用的公共镜像仓库访问速度较慢，导致 Driver Pod 长时间处于镜像拉取阶段。为保证实验顺利进行，将所需镜像同步至华为云 SWR，并统一修改 SparkApplication 中的镜像地址，从而提高镜像获取效率。

在提交 WordCount 和数据分析任务时，还出现过 SparkApplication 创建成功但 Driver Pod 无法正常运行的问题。经过排查发现，部分镜像中缺少分析脚本文件或数据文件。例如镜像中仅包含 Spark 运行环境，而未包含 \verb|analysis.py| 或 \verb|douban_movies.csv|，导致 Driver 启动后立即报错退出。

针对该问题，重新构建 PySpark 镜像，将分析脚本、数据集以及 WordCount 示例程序统一打包到镜像中，并通过 Docker 容器验证镜像内部文件是否存在。经过重新推送镜像后，SparkApplication 能够顺利完成运行。

此外，在性能分析实验中，还遇到 Pandas 和 Matplotlib 依赖缺失的问题。由于基础 PySpark 镜像未预装相关 Python 数据分析库，导致性能对比代码无法正常执行。后续通过在 Dockerfile 中安装 Pandas 和 Matplotlib，并重新构建镜像，成功解决依赖缺失问题。

\subsubsection{OBS或本地数据读取问题}

在数据分析实验中，数据集读取路径配置也是一个重要问题。最初提交 Spark 作业时，程序默认读取本地路径中的 CSV 文件，但镜像内部并不存在对应文件，导致 Spark 报出“Path does not exist”错误。

经过分析后发现，Spark Driver 运行环境与本地开发环境并不一致，必须保证数据文件位于镜像内部指定位置，或通过对象存储服务进行远程访问。因此后续选择将豆瓣电影数据集直接打包到镜像中，并统一放置于 \verb|/opt/spark/work| 目录，从而确保 Driver 和 Executor 能够访问同一数据源。

该问题说明，在分布式环境中必须明确数据与程序的部署位置，仅在本地验证成功并不能保证集群环境能够正常运行。

\subsubsection{性能测试误差问题}

在 Pandas 与 PySpark 性能对比实验中，实验结果并未呈现理想情况下的线性加速现象。理论上 Executor 数量增加后应获得更高的执行效率，但实际测试结果受到任务启动开销、数据规模、序列化开销和 Shuffle 通信等多种因素影响。

特别是在数据规模相对有限的情况下，Spark 作业的启动时间和资源调度时间占据了较大比例，使得并行计算优势无法完全体现。此外，不同运行环境之间的缓存状态、CPU 资源占用情况以及网络负载差异，也会对最终结果产生一定影响。

为降低实验误差，本项目统一采用相同数据集和相同查询逻辑进行比较，并结合 Amdahl 定律对加速比进行分析，而不是单纯以运行时间长短评价并行计算性能。通过理论与实验结果相结合的方式，更能够客观反映分布式计算系统的实际性能特征。
