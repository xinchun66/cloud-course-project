\section{问题记录与解决方案}

课程设计在实施过程中涉及 Docker 容器构建、华为云 CCE 集群运维、Kubernetes 资源编排、Spark Operator 调度以及分布式数据分析等多个技术环节。由于实验环境依赖公网镜像仓库、跨组织 SWR 鉴权以及动态资源调度，部署与验证阶段不可避免地出现若干异常现象。本章仅记录具有代表性的故障现场及其定位思路，正常验收截图已在第三、四章对应任务中呈现；此处着重说明问题成因、排查依据与最终处理方式，以反映项目实施中的真实排错过程。

\subsection{第一部分问题记录}

\subsubsection{镜像构建与推送问题}

\paragraph{Docker Hub 基础镜像拉取超时}

在 T1 应用容器化阶段，本地构建依赖 Redis、Alpine 等基础镜像。实验环境中访问 Docker Hub 国际仓库时多次出现连接超时或层下载中断，导致 \verb|docker build| 无法一次性完成。该问题属于网络链路不稳定所致，而非 Dockerfile 语法错误。处理方式为：对失败层多次重试拉取；优先复用本地已缓存镜像；最终将业务镜像统一推送至华为云 SWR，使 CCE 节点后续从国内镜像仓库拉取，降低对 Docker Hub 的依赖。

\paragraph{镜像组织与标签不一致}

小组分工中，后端与前端镜像由成员 B 构建，CCE 部署由成员 A 在组织 \verb|cloud-course-a| 下执行。若 Deployment 中引用的镜像地址、组织名或 Tag 与 SWR 实际资源不一致，Pod 将陷入 \verb|ImagePullBackOff|。排查时需逐项核对 \verb|swr.cn-north-4.myhuaweicloud.com/<组织>/<镜像>:<Tag| 是否与控制台一致，并统一采用固定版本号（如 \verb|v1|）管理，避免 \verb|latest| 标签漂移。

\paragraph{PySpark 镜像未打包分析脚本}

Spark 镜像初次构建时，若 Dockerfile 中 \verb|COPY| 路径或构建上下文设置不当，镜像内可能缺少 \verb|analysis.py|、\verb|wordcount.py| 或 \verb|douban_movies.csv|。SparkApplication 提交后 Driver 虽能创建，但启动阶段即因找不到入口程序或数据文件而退出。解决方式为：在本地用 \verb|docker run --rm -it <镜像> ls /opt/spark/work| 验证文件清单，修正 Dockerfile 后重新构建并推送。

\subsubsection{CCE 部署与网络访问问题}

\paragraph{私有 SWR 镜像拉取鉴权失败}

T3 应用部署后，backend 与 frontend Pod 曾出现 \verb|ErrImagePull| / \verb|ImagePullBackOff|。执行 \verb|kubectl describe pod| 查看 Events，可见 \verb|401 Unauthorized|，表明 CCE 节点无法匿名拉取私有 SWR 镜像。该问题与业务代码无关，而是镜像仓库权限配置缺失。处理方式为：确认集群命名空间中存在 \verb|default-secret|，并通过 \verb|imagePullSecrets| 将其绑定至 backend 与 frontend Deployment；修复后 Pod 能够正常拉取镜像并进入 Running 状态。

\paragraph{LoadBalancer Service 外部 IP 持续 Pending}

\verb|backend-svc| 创建为 LoadBalancer 类型后，\verb|EXTERNAL-IP| 长时间显示 \verb|<pending>|，导致无法通过公网访问 \verb|/api/ping|。此时 Deployment 与 Pod 可能均已 Running，问题集中在 Service 与 ELB 的绑定环节。

\begin{figure}[H]
  \centering
  \includegraphics[width=0.88\textwidth]{figures_A/T3/15_问题现象_backend_svc外部IP持续Pending.png}
  \caption{backend-svc 的 EXTERNAL-IP 持续为 \texttt{<pending>} 的故障现场}
  \label{fig:ch5-svc-pending}
\end{figure}

图 \ref{fig:ch5-svc-pending} 记录了 \verb|kubectl get svc| 的输出：\verb|backend-svc| 类型为 LoadBalancer，但外部 IP 尚未分配。进一步执行 \verb|kubectl describe svc backend-svc| 可见 CCE 提示未指定 \verb|kubernetes.io/elb.id| 或 \verb|loadBalancerIP|。解决步骤为：在华为云控制台创建共享型公网 ELB，再通过 Service 注解 \verb|kubernetes.io/elb.id=<ELB_ID>| 将负载均衡器绑定至 Service；绑定完成后 Service 获得公网 IP，接口访问恢复正常。

\paragraph{kubectl 集群连接失败}

实验初期曾使用 CloudShell 内网模式的 kubeconfig，其 API Server 地址为 VPC 内网地址，仅能在特定网络环境访问。将该配置复制至独立 ECS 后，\verb|kubectl| 报连接超时。经排查确认问题出在网络访问路径而非集群故障，需按使用场景重新下载公网或内网对应的 kubeconfig 文件。

\paragraph{Kubernetes 资源命名不一致}

在批量 apply YAML 资源时，若 ConfigMap、Secret 或 Service 名称与 Deployment 引用字段存在拼写差异或命名空间不一致，Pod 将因无法挂载配置或解析服务名而启动失败。此类问题需结合 \verb|kubectl describe| 与 \verb|kubectl logs| 中的 Events 与报错信息，对照 YAML 逐项修正。

\subsubsection{PVC 与 HPA 验证问题}

\paragraph{Redis PVC 短暂处于 Pending}

T4 持久化实验中，\verb|redis-data-pvc| 创建后曾短暂处于 Pending 状态。PVC 绑定依赖 StorageClass \verb|csi-disk| 与 Everest 存储插件向底层云硬盘申请卷，资源分配需要一定时间。等待云硬盘创建完成后，PVC 进入 Bound 状态，Redis Pod 即可正常挂载；该现象属于存储Provisioning 的正常等待，而非配置错误。

\paragraph{HPA 压测与指标采集异常}

T6 弹性伸缩验证中遇到三类非致命但影响观测的问题。第一，CloudShell 未预装 \verb|ab|，需改用多进程 \verb|curl| 循环模拟并发负载。第二，停止压测后副本数未及时下降，排查发现多个 \verb|while true; do curl ...; done| 后台任务仍在运行，导致 CPU 指标持续偏高；须通过 \verb|jobs -l|、\verb|pgrep -af curl| 清理残留进程后，HPA 方能触发缩容。第三，HPA 重建后短时间内 CURRENT 指标显示 \verb|<unknown>/60%|，系 Metrics Server 对新 Pod 的指标采集存在延迟，等待约 1 分钟后指标恢复可读。上述问题均已在第三章 T6 实验中处理完毕，此处仅作排错经验归纳。

\subsection{第二部分问题记录}

\subsubsection{Spark Operator 与作业提交问题}

\paragraph{Spark Operator 默认镜像拉取失败}

A-0 环境部署时，\verb|spark-operator-controller| 与 \verb|spark-operator-webhook| 默认引用 \verb|ghcr.io/kubeflow/spark-operator| 镜像，在当前网络环境下拉取不稳定，Pod 长时间处于镜像拉取阶段。处理方式为：将 Operator 镜像同步至华为云 SWR，修改 Deployment 镜像地址，并在 \verb|spark-operator| 命名空间绑定 \verb|imagePullSecrets|。

\paragraph{Driver 内存低于 Spark 最低要求}

WordCount 与 A-3 性能测试均曾将 Driver 内存设为 \verb|256m|。Spark 对 Driver 进程存在最低内存约束（约 450 MiB 以上），低于阈值时 Driver 启动后立即失败。

  \label{fig:ch5-driver-error}
\end{figure}

图 \ref{fig:ch5-driver-error} 显示 SparkApplication 已创建，但 Driver Pod 状态为 Error，说明调度链路正常而运行参数不满足 Spark 要求，需进一步查看 Driver 日志。

\begin{figure}[H]

  \caption{Driver 日志中的 \texttt{INVALID\_DRIVER\_MEMORY} 错误信息}
  \label{fig:ch5-driver-memory}

图 \ref{fig:ch5-driver-memory} 明确给出失败原因：\verb|256m| 低于 Spark 允许的 Driver 内存下限。将 Driver 与 Executor 内存均调整为 \verb|1g| 后，作业能够正常启动并完成。

\paragraph{集群资源不足导致 Executor Pending}

初始集群仅配置 2 个 \verb|c9.large.2| 节点（各 2 vCPU / 4 GiB），Spark 作业申请 2 个 Executor 时，调度器因节点可分配内存不足而无法完成调度，Executor Pod 长期处于 Pending 状态。

  \caption{Executor Pod 因节点内存不足而处于 Pending 状态}
  \label{fig:ch5-exec-pending}
\end{figure}

图 \ref{fig:ch5-exec-pending} 中 \verb|kubectl get pods| 显示 Executor 未被调度至任何节点。结合 \verb|kubectl describe pod| 可见 \verb|Insufficient memory| 事件。

\begin{figure}[H]
  \centering
  \includegraphics[width=0.88\textwidth]{figures_B/A3/a3-exec1-executor-resource-waiting.png}
  \caption{Executor 等待 Kubernetes 调度器分配资源}

图 \ref{fig:exec-waiting} 进一步展示调度器正在尝试为 Executor 分配资源的等待状态。处理方式为：在 CCE 控制台新增 2 个 \verb|c9.large.4| Worker 节点，扩充集群可调度资源后，Executor 成功创建并运行。

\paragraph{跨组织 SWR 镜像拉取权限不足}

A-3 使用的 PySpark 镜像位于成员 B 的 SWR 组织 \verb|xinchunli|，而 Spark 作业默认 ServiceAccount 未绑定对应镜像拉取密钥，Driver 或 Executor 拉取镜像时报权限错误。

\begin{figure}[H]
  \centering
  \includegraphics[width=0.88\textwidth]{figures_B/A3/a3-permission-denied-error.png}
  \caption{Spark Pod 拉取跨组织私有镜像时的权限拒绝错误}
  \label{fig:ch5-permission-denied}
\end{figure}

图 \ref{fig:ch5-permission-denied} 显示镜像拉取阶段出现 \verb|permission denied| 或 \verb|401| 类错误。解决方式为：在作业命名空间创建指向目标 SWR 的 \verb|imagePullSecrets|，并将其绑定至 Spark 使用的 ServiceAccount，使 Pod 具备拉取跨组织镜像的凭证。

\paragraph{Python 依赖库缺失}

A-3 性能对比脚本依赖 Pandas 与 Matplotlib，基础 PySpark 镜像未预装上述库，Driver 执行至性能测试阶段时抛出 \verb|ModuleNotFoundError|。通过在 Dockerfile 中显式安装依赖并重新构建推送镜像解决。

\subsubsection{数据读取与路径配置问题}

Spark Driver 运行于容器内，与本地开发环境的文件路径并不相同。若 SparkApplication 中数据路径仍指向宿主机或本地仓库路径，而镜像内未包含对应 CSV 文件，作业将报 \verb|Path does not exist|。分布式环境下必须保证数据文件已打入镜像固定目录（如 \verb|/opt/spark/work|），或通过 OBS \verb|s3a://| 路径远程读取；仅在本地 \verb|spark-submit| 成功并不能保证 Kubernetes 环境可复现。

\subsubsection{性能对比结果的非线性现象}

A-3 实验中，Pandas 单机耗时（0.50 s）低于 PySpark 单 Executor（1.15 s）与双 Executor（1.16 s），增加 Executor 未带来加速。这并非实验操作失误，而是小数据集下 Spark 启动开销、任务调度、Shuffle 与 K8s Pod 创建成本占比较高所致。该现象已在第四章结合 Amdahl 定律分析；本章不再重复展示性能对比图，仅将其作为分布式计算适用边界的问题加以记录。

\subsubsection{CI/CD 流水线部署问题}

附加题 CI/CD 验证初期，曾尝试在 GitHub Actions hosted runner 中直接执行 \verb|kubectl set image| 更新 CCE Deployment，排查中遇到两类障碍：其一，CloudShell 导出的 kubeconfig 依赖本地证书与私钥文件，且私钥并非 runner 可直接解析的标准 PEM 格式，报错 \verb|tls: failed to find any PEM data in key input|；其二，kubeconfig 默认指向 CCE 内网 API Server 地址，公网 runner 无法访问该内网端点。为保证流程稳定可复现，最终将 Actions 职责收敛为自动构建并推送 SWR，再由 CloudShell 使用同一镜像 Tag 完成 Deployment 更新。

\subsection{本章小结}

本章按实施顺序归纳了课程设计中的主要故障及其处理路径。第一部分中，Docker Hub 拉取不稳定与 SWR 组织/标签不一致影响镜像交付；CCE 部署阶段私有镜像 \verb|401| 鉴权失败与 LoadBalancer 外部 IP Pending 是阻碍公网访问的关键瓶颈；HPA 验证则暴露了压测工具缺失、后台进程残留与指标采集延迟等运维细节。第二部分中，Spark Operator 与 PySpark 作业先后遇到公共镜像拉取困难、Driver 内存低于下限、集群资源不足、跨组织镜像权限拒绝以及 Python 依赖缺失等问题；数据路径配置不当会导致分布式环境下文件找不到；性能对比的非线性结果则提示须结合数据规模解读并行收益。附加题中，监控部署的 Helm 远程仓库访问超时通过离线 Chart 安装解决；CI/CD 验证则因 kubeconfig 私钥格式与内网 API Server 限制，改为 Actions 构建推送 SWR 与 CloudShell 半自动更新 Deployment 的协作模式。

上述问题的共同特征在于：表象往往出现在 Pod 状态或 Service 字段，根因却可能位于网络连通性、镜像权限、资源配额或配置参数等不同层面。通过 \verb|kubectl describe|、Pod 日志与控制台 Events 进行交叉验证，逐项排除假设，是云原生环境排错的基本方法。这些经验为项目最终验收提供了保障，也为后续类似场景的故障定位积累了可参考的处理流程。
