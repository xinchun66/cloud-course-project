\subsection{A-0：Spark环境部署}

为了在 Kubernetes 环境中运行 Spark 作业，本项目采用 Spark Operator 方式部署 Spark 集群。Spark Operator 是 Kubernetes 环境下用于管理 SparkApplication 资源的控制器，能够自动完成 Driver Pod、Executor Pod 的创建、监控与销毁，从而实现 Spark 作业的声明式管理。相比传统 spark-submit 方式，Spark Operator 更符合云原生架构思想，便于与 Kubernetes 的调度、资源管理和监控体系进行集成。

本实验基于华为云 CCE 集群部署 Spark Operator。首先将 Spark Operator 控制器镜像同步至华为云 SWR 镜像仓库，然后通过 Deployment 和 Service 完成部署。安装完成后，通过查看 Spark Operator 控制器 Pod 状态验证服务是否正常运行。

\subsection{A-1：数据清洗}

数据清洗是数据分析流程中的关键步骤，其目标是在保证数据完整性的前提下消除缺失值、异常值和格式不一致等问题，提高后续分析结果的准确性。本实验基于豆瓣电影数据集，利用 PySpark DataFrame API 完成数据加载、缺失值统计和数据清洗工作。

\subsubsection{数据集选择与字段说明}

实验选择豆瓣电影评分数据集作为分析对象。数据集包含电影基本信息、评分信息、国家地区、电影类型以及剧情简介等内容，共计约 6 万条电影记录。

主要字段包括：

\begin{itemize}
\item movie\_id：电影唯一标识；
\item title：电影名称；
\item year：上映年份；
\item rating\_score：平均评分；
\item rating\_count：评分人数；
\item genres：电影类型；
\item countries：国家或地区；
\item directors：导演信息；
\item summary：电影简介。
\end{itemize}

该数据集同时具备结构化属性和文本属性，适合作为 Spark SQL 分析和性能测试的数据来源。

\subsubsection{DataFrame加载与Schema输出}

\subsubsection{缺失字段处理策略一}

对于 movie\_id、title、year、rating\_score 和 rating\_count 等核心分析字段，若存在缺失值，将导致统计结果失真。因此采用删除策略处理。

具体实现方式为：

\begin{center}
dropna(subset=[核心字段])
\end{center}

该策略能够保证参与分析的数据均具备完整关键属性。

\subsubsection{缺失字段处理策略二}

对于 directors、countries、genres、summary 等辅助信息字段，为避免大量数据被删除，采用填充策略处理。

填充值设置如下：

\begin{itemize}
\item Unknown；
\item No Summary。
\end{itemize}

通过 fillna() 方法完成统一填充，使数据集保持完整性。

\subsection{A-2：Spark SQL统计分析}

在完成数据清洗后，利用 Spark SQL 对豆瓣电影数据集进行统计分析。Spark SQL 提供了类似传统关系数据库的查询能力，同时能够充分利用 Spark 分布式计算框架的并行处理优势。本实验设计了四类典型分析任务，分别覆盖 GROUP BY 聚合分析、ORDER BY Top-N 分析、时间趋势分析以及窗口函数分析，以验证 Spark SQL 在大数据分析场景中的应用能力。

\subsubsection{查询一：GROUP BY聚合分析}

第一个查询以电影类型（Genres）为统计对象，计算每种类型对应的电影数量、平均评分以及平均评分人数。首先利用 explode 函数将多类型字段拆分为多行数据，再使用 GROUP BY 完成聚合统计，最后筛选电影数量不少于 5 部的类型，并按照平均评分降序排列。

\begin{figure}[H]
\centering
\includegraphics[width=0.95\textwidth]{figures_B/A2/a2-query1-groupby.png}
\caption{按电影类型统计数量与平均评分}
\label{fig:a2_query1}
\end{figure}

图\ref{fig:a2_query1}展示了不同电影类型的统计结果。从输出可以看到，纪录片、传记、音乐等类型在样本量达到 5 部以上时，平均评分往往高于 8.0，说明小众题材在豆瓣用户群体中更容易获得稳定好评；而剧情、喜剧、动作等商业类型影片数量更多，平均评分却相对分散，部分类型因包含大量粉丝向或续集作品而拉低整体均值。该查询先通过 \verb|LATERAL VIEW explode| 将一部电影的多个类型拆成多行，再按类型聚合，能够避免“一部电影只归属单一标签”带来的统计偏差。结合平均评分人数字段，还可以区分“评分高但受众窄”与“评分高且讨论度高”两类作品，为后续内容推荐或片单策划提供依据。

\subsubsection{查询二：ORDER BY Top-N分析}

第二个查询按照评分人数（$rating\_count$）进行排序，选取评分人数最高的前 10 部电影。评分人数能够反映电影的社会影响力和用户关注程度，因此该分析有助于识别最具代表性的热门电影。

\begin{figure}[H]
\centering
\includegraphics[width=0.95\textwidth]{figures_B/A2/a2-query2-topn.png}
\caption{评分人数最高的Top-10电影}
\label{fig:a2_query2}
\end{figure}

图\ref{fig:a2_query2}给出了评分人数排名前十的电影结果。榜单中多为《肖申克的救赎》《阿甘正传》《泰坦尼克号》等具有跨时代影响力的作品，其评分人数动辄数十万，说明这些影片不仅口碑好，而且被大量用户实际观看并参与打分，结果更具统计代表性。与单纯按 \verb|rating_score| 排序相比，按评分人数排序更能反映“社会共识度”：一部评分 9.0 但仅数千人评价的电影，可能主要来自核心影迷群体，而榜单前列影片则同时经受住了大规模观众的检验。该 Top-N 查询实现简单，但在产品侧常用于首页推荐、热门榜单和舆情监测，是 Spark SQL 中最常见的排序分析模式之一。

\subsubsection{查询三：时间维度趋势分析}

第三个查询按照上映年份进行聚合统计，计算每年的电影数量、平均评分以及平均评分人数，并筛选 1900 至 2030 年之间且样本数量不少于 3 部的年份记录。

\begin{figure}[H]
\centering
\includegraphics[width=0.95\textwidth]{figures_B/A2/a2-query3-year-trend.png}
\caption{电影数量与评分时间趋势分析}
\label{fig:a2_query3}
\end{figure}

图\ref{fig:a2_query3}展示了电影数据在时间维度上的变化情况。可以观察到，20 世纪 90 年代以后各年份的 \verb|movie_count| 明显上升，这与全球电影产量增长、豆瓣收录范围扩大以及用户自发补录老片等因素有关；而 \verb|avg_rating| 在多数年份维持在 7.5--8.5 区间，并未随产量激增而系统性下降，说明用户评分标准在时间上相对稳定。查询中通过 \verb|HAVING COUNT(*) >= 3| 过滤样本过少的年份，可避免个别年份仅有一两部高分电影造成的“虚高均值”。从业务角度看，该趋势图可用于分析电影市场扩张与口碑变化的关系，也为研究“烂片增多是否拉低整体评分”提供了可量化的数据基础。

\subsubsection{查询四：JOIN或窗口函数分析}

第四个查询利用窗口函数 $ROW\_NUMBER()$ 对国家或地区进行分组排序，统计每个国家评分最高的前三部电影。窗口函数能够在保持原始记录粒度的同时完成分组排名分析，是 Spark SQL 中的重要高级特性。

\subsubsection{Amdahl定律加速比分析}

Amdahl 定律用于描述并行计算的理论加速比，其表达式如下：

\[
S(N)=\frac{1}{(1-f)+\frac{f}{N}}
\]

其中，$f$ 表示可并行部分所占比例，$N$ 表示处理器数量，$S(N)$ 表示理论加速比。

\begin{figure}[H]
\centering
\includegraphics[width=0.80\textwidth]{figures_B/A3/a3-amdahl-analysis.png}
\caption{实测加速比与Amdahl理论加速比对比}
\label{fig:a3_amdahl}
\end{figure}

图\ref{fig:a3_amdahl}展示了实测加速比与 Amdahl 理论加速比之间的对比关系。根据实验结果，双 Executor 相比单 Executor 并未获得实际加速效果，说明当前数据规模下并行计算带来的收益不足以抵消系统额外开销。

\subsubsection{非线性加速原因讨论}

实验结果显示，PySpark 双 Executor 的执行时间略高于单 Executor。造成这一现象的主要原因包括：

\begin{enumerate}
\item 数据规模较小，无法充分利用多个 Executor 的计算能力；
\item Spark Driver 启动和 Executor 调度存在固定开销；
\item Shuffle 数据交换和网络通信产生额外成本；
\item 序列化与反序列化过程增加处理时间；
\item Kubernetes 环境下 Pod 创建和资源调度带来额外延迟。
\end{enumerate}

综合来看，Spark 的优势主要体现在大规模数据处理场景。当数据规模达到数 GB 甚至数十 GB 时，分布式并行计算能够显著降低总体执行时间；而对于当前约 6 万条记录的数据集，单机 Pandas 已能够高效完成分析任务，因此表现优于 Spark 集群模式。
