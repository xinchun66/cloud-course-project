\section{第一部分：云计算平台搭建}

本章对应课程设计任务书第一部分“云计算平台搭建”，总分 50 分。该部分以“Flask 后端 API + Redis 数据库 + Nginx 前端页面”为应用对象，完成从本地容器化联调到华为云 CCE 集群部署的全过程。报告按照任务书 T1 至 T6 的顺序组织：T1 说明应用容器化与 SWR 镜像推送；T2 说明 CCE 集群搭建与节点 Ready 验证；T3 说明 Kubernetes 资源部署与公网接口访问；T4 说明 Redis PVC 持久化验证；T5 说明 Nginx 配置以 ConfigMap Volume 形式挂载；T6 说明 HPA 弹性伸缩的配置、压测验证与扩缩容结果分析。

\subsection{任务1：应用容器化}

任务 1 的目标是将后端和前端应用分别容器化，并通过本地联调与 SWR 推送证明镜像可运行、可分发。后端采用 Flask 提供 \verb|/api/ping| 接口，并通过 Redis 客户端验证与 Redis 服务的连接状态；前端采用 Nginx 静态页面，页面中包含学生姓名和学号，满足验收识别要求。完成本地构建后，将 \verb|backend:v1| 和 \verb|frontend:v1| 推送至华为云 SWR，为后续 CCE 部署提供镜像来源。

\subsubsection{后端Dockerfile多阶段构建}

后端 Dockerfile 保留了任务书要求的多阶段构建结构。第一阶段基于 \verb|python:3.11-slim| 安装依赖，并将依赖包安装到 \verb|/build/packages|；第二阶段仍使用轻量级 Python 运行时镜像，只复制依赖包和应用代码，并通过 \verb|PYTHONPATH=/app/packages| 指定依赖搜索路径。该结构将依赖安装过程与运行时环境分离，能够减少运行镜像中不必要的构建缓存和工具链内容。

本项目后端依赖文件中包含 \verb|flask==3.0.0|、\verb|redis==5.0.1| 和 \verb|requests==2.31.0|。其中 \verb|requests| 是在基础模板之外加入的自选 Python 包，满足任务书中“至少加入 1 个自选 Python 包”的要求。

\subsubsection{后端依赖包修改与说明}

后端服务依赖 Flask 提供 HTTP API，依赖 Redis Python 客户端连接 Redis 服务，并额外加入 requests 包以体现依赖扩展能力。虽然当前核心接口主要用于健康检查和 Redis 连接验证，但依赖文件采用固定版本号写法，能够减少镜像构建时由于上游包版本变化导致的不确定性。后端容器暴露 5000 端口，启动命令为 \verb|python app.py|，与 Kubernetes Deployment 中的 \verb|containerPort: 5000| 保持一致。

\subsubsection{Volume挂载与envFrom适用场景对比}

ConfigMap 通过 \verb|envFrom| 注入时，适合传递短小的键值型配置，例如 Redis 主机名、端口、运行环境等；应用读取这些配置通常依赖环境变量，形式简单，适用于启动参数和少量配置项。ConfigMap 通过 Volume 挂载时，适合传递完整配置文件，例如 Nginx 配置、应用配置模板或多行脚本；应用可以像读取普通文件一样读取配置内容，结构更完整，也更适合复杂文本配置。

本项目中后端 Redis 地址和端口属于典型键值配置，因此使用 ConfigMap 环境变量注入；前端 Nginx 反向代理配置属于完整文件，因此使用 ConfigMap Volume 挂载更合适。二者共同体现了 Kubernetes 配置外置化的两种常见方式。

\subsection{任务6：HPA弹性伸缩}

任务 6 要求为后端 Deployment 配置 Horizontal Pod Autoscaler（HPA），并通过负载压测验证 Pod 副本数能够随 CPU 利用率动态调整：在压测期间由 1 个扩展至 2 个或更多，停止压测并等待稳定窗口结束后缩回 1 个。HPA 是 Kubernetes 实现应用层弹性伸缩的核心机制，其决策依赖 Metrics Server 采集的资源指标，因此本任务既考察 HPA 资源配置的正确性，也考察指标链路可用性与扩缩容行为的可观测性。

实验在已完成 T3 部署的 CCE 集群上进行。伸缩目标为 \verb|backend| Deployment，对外压测入口为 \verb|backend-svc| 绑定的 ELB 公网地址，压测路径为 \verb|/api/ping|。为便于观察副本变化，实验前先将 backend 副本数手动调整为 1，再创建 HPA 资源并施加持续并发请求，最后清理压测进程并观察自然缩容过程。

\subsubsection{Metrics Server可用性验证}

HPA 控制器本身不直接采集 Pod 资源使用情况，而是基于 Metrics Server 提供的聚合指标计算期望副本数。因此，在创建 HPA 之前，需要确认集群中 Metrics Server 已安装且 \verb|kubectl top| 命令能够返回有效数据。实验中通过 \verb|kubectl get pods -n kube-system| 确认 Metrics Server Pod 处于 Running 状态，并执行 \verb|kubectl top nodes| 查看各 Worker 节点的 CPU 与内存使用量。

\reportfig{figures_A/T6/01_metrics_server可用top_nodes.png}{Metrics Server 可用性及节点资源指标验证截图}{fig:t6-metrics-server}

图 \ref{fig:t6-metrics-server} 表明 Metrics Server 工作正常，\verb|kubectl top nodes| 能够输出节点名称、CPU 使用量、CPU 使用率、内存使用量及内存使用率。该结果是 HPA 能够读取 Pod CPU 指标并进行扩缩容决策的前提条件；若 Metrics Server 不可用，HPA 的 CURRENT 指标将长期显示为 \verb|<unknown>|，控制器无法触发有效伸缩。

\subsubsection{后端HPA资源配置}

本项目 HPA 定义见 \verb|k8s/backend-hpa.yaml|，采用 \verb|autoscaling/v2| API，资源名称为 \verb|backend-hpa|，作用对象为 \verb|backend| Deployment。关键参数设置为 \verb|minReplicas=1|、\verb|maxReplicas=4|，并以 Pod 平均 CPU 利用率为伸缩依据，目标值为 60\%。该配置与任务书模板一致：当 backend Pod 的平均 CPU 利用率持续高于 60\% 时，HPA 控制器逐步增加副本数，上限为 4；当负载降低并满足缩容稳定窗口要求后，副本数回落至最小值 1。

图 \ref{fig:t6-hpa-created} 显示 \verb|backend-hpa| 已成功创建，CURRENT 指标与 TARGET 指标均为 CPU 利用率，副本数范围限定在 1 至 4 之间。

\subsubsection{停止压测后的缩容过程验证}

停止压测后，HPA 并不会立即减少副本数。Kubernetes 为缩容设置了稳定窗口（stabilization window），以避免因指标瞬时波动导致副本数频繁震荡。实验中首先终止前台压测命令，随后通过 \verb|jobs -l| 与 \verb|pgrep -af curl| 排查并清理仍在运行的后台 \verb|curl| 循环任务；若残留进程持续发送请求，CPU 指标将长期高于目标值，HPA 便无法进入缩容阶段。

\reportfig{figures_A/T6/07_停止压测后HPA缩容状态.png}{停止压测后 HPA 处于缩容过渡状态截图}{fig:t6-scale-down-transition}

图 \ref{fig:t6-scale-down-transition} 展示了停止压测后、副本数尚未完全回落的过渡状态。该截图说明缩容过程存在可观测的延迟：Metrics Server 指标采集、HPA 重新评估以及缩容稳定窗口共同作用，使副本数变化滞后于负载变化，这符合 Kubernetes 自动伸缩的设计预期。

\subsubsection{实验问题与处理}

本任务实施过程中遇到三类典型问题。其一，CloudShell 环境缺少 \verb|ab| 工具，已通过多进程 \verb|curl| 循环替代并发压测，效果等价于对后端接口施加持续负载。其二，初次停止压测后副本数未及时下降，经排查发现多个 \verb|while true; do curl ...; done| 后台任务仍在运行；使用 \verb|kill| 与 \verb|pkill -f| 清理残留进程后，CPU 指标恢复正常，HPA 随即触发缩容。其三，HPA 重建后短时间内出现 \verb|<unknown>/60%| 指标，系 Metrics Server 对新 Pod 的指标采集存在延迟所致，等待约 1 分钟后指标恢复可读，HPA 计算结果趋于稳定。

\subsubsection{扩容延迟、冷却机制与工程意义分析}

综合上述实验过程，HPA 扩缩容行为呈现出“扩容相对积极、缩容相对保守”的特征。扩容延迟主要来源于 Metrics Server 采集周期、HPA 控制器评估间隔、Pod 调度与容器启动时间等环节；缩容则受稳定窗口约束，需等待指标持续低于阈值后才逐步减少副本。对于本课程设计中的 Flask 后端而言，HPA 的工程价值体现在两方面：在访问高峰时自动增加副本以分担请求压力，提升服务可用性；在负载回落后自动回收多余 Pod，降低 CCE 节点的 CPU 占用与按需计费成本。T6 实验结果表明，本项目 backend 服务的 HPA 配置正确、指标链路可用，扩缩容行为符合 Kubernetes 自动伸缩机制的预期，任务验收要求已得到满足。
